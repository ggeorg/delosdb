DelosDB overlay: F07 sort decomposition diagnostic

Purpose:
- Explain why canonical F07 SORT_FULL remains far slower on Gen2 after the storage
  modernization tranches.
- Distinguish optimizer/access-path error from raw input cost and genuine sort/materialization cost.
- Make no production storage or optimizer change.

Canonical evidence motivating this diagnostic:
- SERVER/8c SORT_FULL:
    Delos Heap          ~1107.8 tx/s
    Gen2 MVCC           ~295.8 tx/s
    upstream Derby      ~1134.2 tx/s
    PostgreSQL          ~1108.5 tx/s
- Gen2 IQR/median ~2.0%, max/min ~1.067x.
- Heap, upstream Derby and PostgreSQL are effectively tied, so the remaining deficit is Gen2-specific.

Diagnostic:
- Embedded Heap and Gen2 in one database.
- 10,000 rows, payload 128, FULL_INDEXED fixture, explicit statistics refresh.
- Six matched variants:
    heap-input
    mvcc-input
    heap-natural-sort
    mvcc-natural-sort
    heap-forced-table-sort
    mvcc-forced-table-sort
- Input variant forces TABLE_SCAN and omits ORDER BY.
- Natural sort uses:
    select id, quantity from T order by quantity desc, id
- Forced sort uses the same ORDER BY plus DERBY-PROPERTIES index=null.
- Captures EXPLAIN ANALYZE for every variant.
- Runs 8 warmups, 9 measured rounds, 3 executions/sample.
- Writes repeated samples, dispersion, plan/operator summary, full EXPLAIN captures,
  semantic fingerprints, and a classification.

Interpretation:
- Natural MVCC plan differs from forced TABLE_SCAN and forced is materially faster
    => optimizer/access-path costing problem.
- Raw input is already much slower and forced sort ratio tracks input ratio
    => Gen2 sort input remains primary.
- Forced sort ratio grows far beyond input ratio
    => Gen2-specific sort/materialization layer is primary.
- Otherwise
    => move to JFR attribution.

New Gradle task:

- No canonical benchmark thresholds.
- No SQL semantics.
