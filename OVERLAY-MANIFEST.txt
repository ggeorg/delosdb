DelosDB overlay: F07 materialized-vs-streaming TABLE_SCAN falsification

Purpose:
- Test whether eager whole-table List<VisibleRow> materialization is the dominant remaining
  Gen2 F07 cost before changing holdable scan architecture.
- Reuse the existing StreamingBatchScan implementation under CLOSE_CURSORS_AT_COMMIT,
  where streaming is already supported and semantically reachable.
- Keep projected CURRENT enabled in both lanes so unnecessary wide-payload decoding does not
  confound this experiment.

Canonical evidence motivating this diagnostic:
- Projected CURRENT improves canonical SERVER F07 only modestly:
    Gen2 ~295.8 -> ~316.8 tx/s (+7.1%)
    Gen2/PostgreSQL ~26.7% -> ~28.3%
- Candidate run is valid and semantic fingerprints match, so wide payload decode is real
  but not the main remaining F07 deficit.
- Current materialized Gen2 TABLE_SCAN still builds List<VisibleRow> for the whole table before
  BulkTableScanResultSet can consume row 1, after which SORT materializes rows again.

Matched A/B:
- Embedded 10,000-row F07 fixture, FULL_INDEXED.
- 8 clients.
- CLOSE_CURSORS_AT_COMMIT in both lanes.
- Four measured variants in each lane:
    heap-input
    mvcc-input
    heap-sort
    mvcc-sort
- Raw input forces TABLE_SCAN and omits ORDER BY.
- Sort uses the real F07 query:
    select id, quantity from T order by quantity desc, id
- projected CURRENT = true in both lanes.
- single-pass/reusable flags = true in both lanes.
- physical scan cost = true.
- physical RowLocation cost = true.
- fast-visibility / skipped-tags / lazy-field streaming experiments = false.
- OFF lane: streamingBulkScan=false.
- ON lane: streamingBulkScan=true.
- 3 warmup rounds, 7 measured rounds, 2 executions/client/round.
- Semantic fingerprints required to match.
- IQR/MAD and max/min <=1.20 run-range validity recorded.

New tasks:
- :delosdb-tests:runDelosGen2C3F07StreamingOffDiagnostic
- :delosdb-tests:runDelosGen2C3F07StreamingOnDiagnostic
- :delosdb-tests:runDelosGen2C3F07StreamingABDiagnostic

Interpretation:
- Strong MVCC input + sort improvement with Heap flat:
    eager whole-scan materialization is a primary F07 cause.
- Only a few percent improvement:
    whole-list materialization is not the main remaining F07 cause.
- Input improves strongly but sort does not:
    a sort-side materialization/copy layer remains dominant.

What this does NOT change:
- No production code.
- No holdable cursor behavior.
- No canonical F07 task or thresholds.
- No optimizer cost formula.
- No MVCC visibility, RowLocation, WAL, undo, recovery, or vacuum behavior.
