DelosDB overlay: F07 projected-CURRENT matched A/B harness

Purpose:
- Test the JFR/source-derived F07 hypothesis that Gen2 TABLE_SCAN wastes CPU and allocation
  decoding/cloning payload columns that the query does not request.
- Reuse the existing projected-CURRENT implementation as a diagnostic only.
- Do not promote or alter production behavior.

JFR/source evidence:
- F07 SELECT returns only id, quantity.
- With projected-current disabled, MaterializedCurrentScanDecoder uses currentProjection=null.
- currentPayloadDescriptor therefore fetches every CURRENT payload column.
- Gen2 JFR input/sort stacks include StoredPage/StoreTypeUtil decode,
  StoreValueCopySupport.tryCloneValue, MaterializedCurrentScanDecoder.decode,
  currentValues and currentVisibleRow.
- Gen2 allocation samples contain SQLVarchar/String work not requested by id,quantity.
- No F02-style ReentrantReadWriteLock/monitor hotspot appears in F07.

Harness change:
- Existing runDelosGen2C3F07EmbeddedConcurrencyDiagnostic now accepts:
    -Pdelosdb.benchmark.mvccGen2ProjectedCurrentRead=true|false
- Default remains false.
- Phase-2R summary records projectedCurrentRead=true|false.

Matched experiment:
- Run the same diagnostic once OFF and once ON.
- Each lane measures Heap/Gen2 raw input and SORT at 1 and 8 clients.
- All SQL, fixture shape, statistics, concurrency, rounds and semantic checks remain identical.

Important scope:
- This does NOT reopen projected-current as the primary F02 solution.
- The hypothesis is specifically F07/materialized TABLE_SCAN input after JFR showed
  unnecessary wide CURRENT payload decoding.

What this does NOT change:
- No production storage source.
- No optimizer/sort code.
- No canonical F07 sentinel.
- No benchmark thresholds.
- No MVCC visibility, RowLocation, WAL, undo, recovery or vacuum behavior.
