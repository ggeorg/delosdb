DelosDB overlay: F07 embedded concurrency decomposition

Purpose:
- Explain why canonical SERVER/8-client F07 is ~3.75x slower on Gen2 while the
  single-client sort decomposition shows only ~1.5-1.7x Gen2/Heap ratios.
- Isolate whether concurrency collapse occurs in raw Gen2 TABLE_SCAN input
  before SORT or only when ORDER BY/SORT runs concurrently.
- Make no production storage, execution, or optimizer change.

Diagnostic:
- Embedded Heap and Gen2 in one database.
- 10,000 rows, payload 128, FULL_INDEXED fixture, explicit statistics refresh.
- Four logical variants:
    heap-input
    mvcc-input
    heap-sort
    mvcc-sort
- Each variant is measured at:
    1 client
    8 clients
- Raw input forces TABLE_SCAN and omits ORDER BY.
- Sort uses the real F07 SQL:
    select id, quantity from T order by quantity desc, id
- 3 warmup rounds.
- 7 measured rounds.
- 1-client: 3 executions/client/round.
- 8-client: 2 executions/client/round.
- Threads start each round behind a barrier.
- Every execution validates row count and semantic fingerprint.

Evidence:
- Per-round throughput samples.
- Median/IQR/MAD validity.
- max/min run-range ratio with explicit 20% validity signal.
- Heap and Gen2 1c->8c scaling.
- Gen2/Heap ratio for raw input at 1c and 8c.
- Gen2/Heap ratio for SORT at 1c and 8c.
- Classification:
    MVCC_TABLE_SCAN_CONCURRENCY_PRIMARY
    MVCC_SORT_CONCURRENCY_PRIMARY
    MIXED_CONCURRENCY_REQUIRES_JFR

Interpretation:
- Raw input and SORT both lose scaling similarly on Gen2:
    TABLE_SCAN/input concurrency is primary.
- Raw input scales near Heap but SORT collapses:
    sort/materialization concurrency is primary.
- Mixed shape:
    profile the 8-client path with JFR next.
