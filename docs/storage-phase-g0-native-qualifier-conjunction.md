# Storage Phase G0 — Native Qualifier Conjunction Cleanup

Status: active cleanup slice before G1 range predicates.

Phase F proved native Derby execution for SELECT, INSERT, DELETE, UPDATE, and
bridge bypass. Before adding range operators in G1, the native table-scan path
needs one bounded semantic cleanup for multi-predicate equality WHERE clauses.

Derby's generated qualifier layout is:

```text
qualifiers[0][0..N]      -> leading AND qualifiers
qualifiers[1..M][0..K]   -> later OR predicate groups, ANDed with qualifiers[0]
```

`DelosTableScanResultSet` already accumulates the leading AND equality
qualifiers. The missing piece was lower in `EngineMvccTableAccess`: after it
selects one equality as the pushed/index candidate, any remaining equality
filters must still be applied to the candidate rows.

G0 adds that leftover equality filtering inside the native table-access scan.
This keeps the access-path optimization seam while making queries like:

```sql
SELECT * FROM APP.T WHERE id = 1 AND kind = 'target'
```

semantically correct.

Verification:

```bash
./gradlew verifyStoragePhaseG0NativeQualifierConjunction storagePhaseC7StabilizationSmoke
```

The smoke proves:

```text
SELECT * FROM APP.T WHERE id = ? AND kind = ?
  -> native Derby execution path
  -> multiple equality predicates accumulated
  -> pushed equality plus leftover equality filtering
  -> bridge not called

SELECT * FROM APP.T WHERE id = ? OR kind = ?
  -> native path remains unsupported for OR-shaped predicates
  -> bridge not called
```

No new bridge route. No regex route. No generated bytecode shape change. No
source/doc text-token report guard.
