# F2.2 — ResultSetFactory metadata lookup preparation

F2.1 made `TableDescriptor.storageProviderName` persistent through
`SYSTABLES.STORAGEPROVIDER`. F2.2 prepares the next native execution step without
changing execution behavior yet.

The key source fact for F3 is that `GenericResultSetFactory.getTableScanResultSet`
receives the generated scan's `tableName` string and the `Activation`. From the
activation we can reach the `LanguageConnectionContext`, then the
`DataDictionary`, then the table descriptor. That makes the provider-aware branch
workable at the existing factory boundary without changing `FromBaseTable.generate()`
or `AsmJava`.

F2.2 adds `DelosTableScanProviderLookup` as the bounded lookup seam:

```text
LanguageConnectionContext + tableName
  -> DataDictionary / SchemaDescriptor
  -> TableDescriptor.storageProviderName
```

This phase deliberately adds **no ResultSetFactory branch yet**. It does not create
`DelosTableScanResultSet`, does not change generated bytecode, and does not route
queries to Delos native execution. That is F3.

The smoke proof creates a `USING delos_mvcc` table and a default heap table, restarts
the database, and verifies the lookup helper can resolve both one-part and two-part
table names from persisted catalog metadata while the transitional SQL bridge remains
unused.
