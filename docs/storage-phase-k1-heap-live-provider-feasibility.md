# Storage Phase K1: heap live-provider feasibility gate

## Decision

**Answer A-lite.** The inspected source supports an incremental route toward A, but it does not support turning heap into a full live Delos provider now.

- Heap scan/cost live-provider parity is incrementally feasible.
- Heap mutation and locking parity should be deferred.
- L1 should stay MVCC-specific unless a later heap proof shows heap can implement the same contract honestly.

K1 is a decision and guard milestone only. It does not change SQL behavior, generated bytecode, optimizer behavior, heap routing, mutation routing, or locking behavior.

## Scope kept closed in K1

K1 deliberately does **not** do any of the following:

No heap routing change means default-provider heap SELECT remains Derby-native in K1.

- no heap activation;
- no live heap provider;
- no `FromBaseTable.generate()` change;
- no ASM/emission change;
- no optimizer behavior change;
- no production SQL behavior change;
- no `RowChangerImpl` replacement;
- no generic row-lock or row-reservation API;
- no bridge resurrection.

## Current provider truth

The inspected DelosDB source currently has one live Delos native provider:

```text
delos_mvcc
```

The default heap provider is still Derby-native. Its Delos-side class is still a proof adapter:

```text
EngineHeapTableAccessProof
```

`DelosNativeTableRegistry` is still delos_mvcc-only. It opens native execution access only for a table whose persisted provider is `delos_mvcc`, and its `NativeExecutionTableAccess` wraps `EngineMvccTableAccess`.

`EngineHeapTableAccessProof` is intentionally not a live provider. Its public scan and mutation methods still throw proof-only exceptions that state the actual heap path remains `TableScanResultSet`, `RowChangerImpl`, and `ConglomerateController`.

## K1 questions

### 1. Can heap scan be exposed through `DelosTableAccess` without badly replacing `TableScanResultSet`?

**Yes, but only incrementally and not in K1.**

The current heap read path is still Derby's inherited scan path:

```text
FromBaseTable.generateResultSet(...)
  -> ResultSetFactory table-scan method
  -> GenericResultSetFactory.getTableScanResultSet(...)
  -> TableScanResultSet
  -> TransactionController.openCompiledScan(...)
  -> ScanController
```

`TableScanResultSet.openScanController()` is still the place that opens the real heap scan through `TransactionController.openCompiledScan(...)`. `TableScanResultSet` also owns the fetch loop through `ScanController.fetchNext(...)` and row-location fetch through `ScanController.fetchLocation(...)`.

However, `GenericResultSetFactory.getTableScanResultSet(...)` is already the result-set branch point. It already builds `TableScanResultSetParameters`, asks `DelosTableScanResultSet.createIfEnabled(params)`, and otherwise falls back to `new TableScanResultSet(params)`. That makes scan/cost parity feasible later without changing `FromBaseTable.generate()` or generated bytecode.

The safe later shape is M1/M2, not K1:

```text
M1: heap scan candidate, no SQL routing
M2: optional property-gated heap scan shadow branch
```

### 2. Can heap `RowLocation` be wrapped honestly as `DelosRowIdentity`?

**Yes, as a heap-local identity wrapper only.**

`EngineStoreRowLocationBridge` already converts Derby engine row-location values into the storage-neutral `StoreRowLocation` shape used by the proof adapter. `EngineHeapTableAccessProof.rowIdentity(Object rowLocation)` wraps that store row location as a `HeapRowIdentity` whose provider name is `heap`.

This is honest for identity transport, but it is not a mutation contract by itself. The identity remains meaningful only to the heap path that understands Derby row locations and `ConglomerateController` operations.

### 3. Can `GenericResultSetFactory` branch safely for default-provider heap?

**Yes later, only under an explicit shadow/live gate. Not in K1.**

`GenericResultSetFactory` is already the native branch point for table scans. `DelosTableScanResultSet.createIfEnabled(params)` currently declines the default provider by returning empty when `lookup.get().isDefaultStorageProvider()` is true. That preserves ordinary heap SELECT behavior.

A future heap branch can be added at this same factory boundary without touching `FromBaseTable.generate()` or bytecode generation, but it must be property-gated until the heap scan candidate is proven. The correct future order is:

```text
M1: EngineHeapTableAccessLiveCandidate.scan(...), no SQL routing
M2: property-gated heap scan shadow branch
M3: supported heap SELECT live route
```

### 4. Are heap mutations too tied to `RowChangerImpl` / `ConglomerateController` for now?

**Yes. Defer heap mutation parity.**

The current mutation path is still deeply Derby-native:

```text
INSERT:
  InsertResultSet
    -> RowChangerImpl
    -> ConglomerateController.insert(...)
    -> ConglomerateController.insertAndFetchLocation(...)

DELETE:
  DeleteResultSet
    -> CursorResultSet.getRowLocation()
    -> RowChangerImpl
    -> ConglomerateController.delete(...)

UPDATE:
  UpdateResultSet
    -> CursorResultSet.getRowLocation()
    -> RowChangerImpl
    -> ConglomerateController.replace(...)
```

`RowChangerImpl` also coordinates index maintenance through `IndexSetChanger`, lock mode/open mode choices, changed-column bitsets, deferred work, and row-location handling. A live heap mutation contract should not be invented until a later N1 proof demonstrates that this behavior can be represented honestly.

### 5. Does a future lock/reservation API need to be MVCC-specific first?

**Yes.**

`DelosMutationPreparation` is currently honest: it prepares/validates mutation context, but it explicitly does not claim to be a lock or reservation. That should remain true for the generic mutation contract.

Heap locking is not naturally an MVCC-style `tryLock` surface. The inspected Derby btree locking classes split behavior across isolation-specific policies:

- `B2IRowLocking1`
- `B2IRowLocking2`
- `B2IRowLocking3`
- `B2IRowLockingRR`

Those policies coordinate row locking, read-lock release, previous-key locking, no-wait/latch behavior, and qualification-time unlock decisions with the underlying conglomerate and scan machinery. That is different from a provider-level MVCC reservation contract.

Therefore L1 should stay MVCC-specific, for example with a delos_mvcc-only reservation surface, unless later heap proof changes this.

## Reference-source comparison

### PostgreSQL

PostgreSQL's table access method interface separates scan, mutation, lock, size estimate, and planner-cost concerns in `TableAmRoutine`. Heap implements those callbacks in `heapam_handler.c`. This supports the DelosDB K1 conclusion: scan/cost capability can mature independently before mutation and locking are made provider-generic.

### MariaDB

MariaDB persists parser-owned engine/provider choice through CREATE TABLE handling and resolves that choice to a `handlerton`/`handler`. Its handler API has separate wrappers for random scan, write, update, delete, external locking, and optional engine SELECT handling. This supports the DelosDB rule that provider selection can be parser/catalog-owned while execution capabilities remain segregated.

### Apache Calcite

Calcite keeps `Table`, `ScannableTable`, `FilterableTable`, `ProjectableFilterableTable`, and `ModifiableTable` separate. Filterable tables consume only the filters they can implement and leave the rest to the planner/executor. `TableModify` is distinct from `TableScan`, and `Convention.NONE` must be converted to an implementable convention before execution. This supports the DelosDB rule: do not add a generic contract method until at least two providers can implement it honestly.

## Guard meaning

The K1 guard proves current truth only:

- bridge files remain absent from active execution/source;
- heap default-provider SELECT still uses Derby-native routing;
- delos_mvcc SELECT still uses the Delos native route;
- `GenericResultSetFactory` remains the scan branch point;
- heap mutations still depend on `RowChangerImpl` and `ConglomerateController`;
- `EngineHeapTableAccessProof` remains proof-only;
- no live heap Delos routing has accidentally appeared;
- this document records the A-lite decision.

The safest route remains:

```text
L4  — optimizer consumption for delos_mvcc

N1  — heap mutation mapping proof

```
