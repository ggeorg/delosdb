# F3.2 — DelosTableScanResultSet skeleton

F3.2 is the first proof that the native Derby execution seam can return a
Delos-owned result set without changing generated bytecode.

The generated activation still emits the existing Derby table-scan factory call.
The branch lives inside `GenericResultSetFactory`, using the provider metadata
lookup prepared in F2.2 and observed in F3.1.

```text
generated activation
  -> ResultSetFactory.getTableScanResultSet(...) or getBulkTableScanResultSet(...)
  -> GenericResultSetFactory
  -> DelosTableScanProviderLookup
  -> DelosTableScanResultSet skeleton
```

The branch is property-gated for the proof. Normal execution still uses Derby's
existing heap scan result sets unless the F3.2 proof property is explicitly set.

Non-goals:

```text
no FromBaseTable.generate() change
no AsmJava change
no ResultSetFactory interface shape change
no getDelosTableScanResultSet(...) method
no EngineMvccTableAccess.scan(...) yet
no row materialization yet
```

The skeleton fails loudly at open time. That is intentional. It proves the
factory can return a Delos result-set object while preventing a false claim that
MVCC scanning works natively.

F4 replaces this sentinel with real scan execution:

```text
Qualifier[][]
  -> column ordinal to ColumnDescriptor
  -> StoreDataValue to native comparable value
  -> DelosPredicate
  -> EngineMvccTableAccess.scan(...)
  -> Derby ExecRow materialization
```
