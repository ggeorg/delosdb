# DelosDB architecture

## System boundary

DelosDB is one Derby-compatible relational database engine for embedded JDBC and DRDA clients.

```text
SQL text
  -> parser and binder
  -> optimizer
  -> generated activation class
  -> result-set execution
  -> Derby transaction control
  -> access method
       -> inherited heap
       -> delos_mvcc
  -> Derby RawStore
  -> JDBC or DRDA result
```

Storage selection does not create a second SQL engine, catalog, transaction manager, network
protocol, or durable-store authority.

## SQL compilation and generated classes

Compiler nodes use the inherited generation boundary:

```text
JavaFactory
ClassBuilder
MethodBuilder
LocalField
```

`ClassFileJava` is the sole production implementation. It emits activation classes with JDK 25
`java.lang.classfile`.

Permanent properties:

```text
52 frozen contract methods
43 MethodBuilder signatures
10 executable behavior groups
38-method deterministic fixture
3465 generated bytes
SHA-256 31df8ee46dcc6256a7ad556c90d5772e69c8656670c4356cd0df3205a47abefe
```

Only `ClassFileJava` and the built-in verifier may use the Class-File API directly. External module
properties cannot replace the `JavaFactory`. There is no ASM dependency, fallback backend, or normal
runtime selector.

## Transaction and storage authority

Derby transaction control remains the database transaction boundary. Heap and MVCC participate
through access-method and RawStore contracts.

```text
one Derby RawStore
    -> inherited heap access method
    -> DelosDB MVCC access method
```

The MVCC access method owns logical semantics:

```text
MvccTransactionId
MvccCommitSequence
statement and transaction snapshots
row/version identity
visibility
write conflicts
version chains
retention and vacuum decisions
```

RawStore owns physical persistence and recovery:

```text
containers and pages
logging and undo
transaction decision durability
checkpoint and recovery integration
backup and database lifecycle
file and memory database storage
```

There is no external MVCC directory, second WAL, dual write, fallback store, or transitional runtime
switch.

## Heap compatibility

The inherited heap remains the default access method and compatibility anchor. DelosDB preserves
supported Derby databases, SQL behavior, catalogs, SQLStates, JDBC surfaces, and DRDA protocol
semantics unless a deliberate documented difference applies.

## MVCC access method

`USING delos_mvcc` persists the table provider identity and routes table/conglomerate operations to
the RawStore-backed MVCC implementation. The provider supports file and named memory databases and
participates in Derby transaction, shutdown, recovery, backup, and DRDA lifecycles.

Unsupported combinations fail before mutation. Current examples include MVCC `SERIALIZABLE`, XA
writes, and durable Java-object/UDT values. The current `SERIALIZABLE` rejection is a truthful
pre-1.0 implementation boundary, not the intended final v1 isolation contract; true MVCC
`SERIALIZABLE` remains required before v1 release.

## Module boundaries

Core production ownership is separated as follows:

| Module | Responsibility |
|---|---|
| `delosdb-commons` | shared compatibility and utility contracts |
| `delosdb-runtime-api` | neutral runtime-facing APIs |
| `delosdb-spi` | provider-neutral external-index contracts |
| `delosdb-derby-store-api` | neutral storage/access-method contracts |
| `delosdb-storage-derby` | inherited heap and RawStore implementation |
| `delosdb-storage-mvcc` | MVCC provider and semantics |
| `delosdb-engine` | SQL, catalogs, execution, embedded JDBC |
| `delosdb-client` | DRDA client |
| `delosdb-server` | DRDA server |

The engine must not depend directly on the MVCC implementation. Providers are discovered through
neutral contracts and runtime provider metadata.

Retired modules and artifacts:

```text
delosdb-storage-api
delosdb-storage-io
delosdb-storage-bridge
```

Lucene remains an optional/deferred derived provider. It must never become a transaction or commit
authority.

## Readable-engine diagnostics

DelosDB exposes the selected optimizer plan through immutable `StablePlanModel`, deterministic
`EXPLAIN`, and bounded query-only `EXPLAIN ANALYZE`. Execution evidence is correlated to stable plan
node ids through generated `resultSetNumber` identity and reuses existing Derby runtime statistics plus
heap/MVCC scan information. It does not reconstruct a plan from runtime classes or feed diagnostics back
into optimizer/executor state.

For MVCC scans, ANALYZE can expose the exact scan snapshot sequence and concise read-path/version
traversal diagnostics where existing counters prove them. Unmeasured paths remain explicitly
`NOT_MEASURED` or `UNKNOWN` rather than adding profiling work to ordinary row loops.

See [`READABLE-ENGINE.md`](READABLE-ENGINE.md) for the SQL contract and one production end-to-end trace.
