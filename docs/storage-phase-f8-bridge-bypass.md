# Storage Phase F8 / G6 — bridge bypass and retirement

F8 introduced the corrected bridge-bypass strategy: the pre-parse
`EmbedStatement` hook must not try to inspect SQL text and guess whether a
statement targets a metadata-backed `delos_mvcc` table. That decision belongs
after Derby parse/bind/catalog metadata, not inside a regex bridge.

G6 completes that strategy by retiring `VersionedStorageSqlBridge` as an
automatic SQL fallback. Normal execution no longer has a compatibility property
that can re-enable pre-parse bridge interception.

```text
EmbedStatement
  -> VersionedStorageSqlBridge.isInterceptionEnabled() == false
  -> Derby parser / binder / optimizer / generated activation
  -> native ResultSetFactory / ConstantAction provider-aware seams
  -> Delos result set / mutation result set / table access
```

The old direct bridge APIs may remain temporarily as legacy scaffolding or test
helpers, but they are not a production SQL route and they are not wired into the
normal Phase F/G verification path.

Current invariants:

```text
- No normal execution mode enables VersionedStorageSqlBridge interception.
- delosdb.storage.sqlBridge.compatibility must not re-enable interception.
- Native Phase F/G smokes create and populate provider tables through Derby paths.
- CREATE TABLE ... USING delos_mvcc registers provider storage from Derby metadata.
- INSERT / DELETE / UPDATE / SELECT use native provider-aware result-set seams.
- CREATE INDEX resolves provider metadata from TableDescriptor, not SQL regex.
```

This leaves the target architecture unchanged:

```text
SQL
  -> Derby JavaCC parser
  -> Derby binder / metadata
  -> Derby optimizer
  -> generated activation / ConstantAction
  -> existing ResultSetFactory family
  -> provider-aware native branch
  -> Delos result set / Delos table access
```

F8/G6 do not add a new bridge SQL route, regex route, generated bytecode method,
or `ResultSetFactory` interface method.
