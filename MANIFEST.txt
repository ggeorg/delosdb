DelosDB Gen2-C3 F05 version-page run reuse A/B overlay

Purpose
-------
Falsify whether repeated RawStore version-page reacquisition is a primary
contributor to the remaining matched-plan F05 MVCC base-fetch gap.

Current evidence
----------------
After directory-head trimming, read-head template reuse, and single-pass
hinted-version decode:

  Heap = 0.761323 ms/execution
  Gen2 = 1.280053 ms/execution
  ratio = 1.681353x

Projected-version payload-holder reuse removed the SQLInteger.cloneValue
allocation hotspot but regressed Gen2 slightly:

  Gen2 = 1.305144 ms/execution

That hypothesis is therefore rejected as the primary fix.

In the latest raw JFR, approximately 97% of sampled PageKey allocation weight
on the Gen2 side comes from:

  MvccRawStoreVersionReader.findByHint
  -> ContainerHandle.getPage
  -> FileContainer.getUserPage
  -> new PageKey(...)

Experiment
----------
OFF by default:
  existing per-fetch version-page getPage/unlatch behavior

ON:
  -Ddelosdb.experimental.mvccReuseVersionHintPageRun=true

When enabled, MvccRawStoreVersionReader retains a successfully decoded hinted
version page across consecutive hinted lookups to the same page. On page
number change, fallback, close, failed lookup, or exception, the retained page
is released.

This experiment intentionally tests the cost of repeated page reacquisition.
It is NOT a production design: holding a RawStore page latch across base-row
fetch calls can alter writer concurrency and must not be promoted directly.

No changes
----------
No visibility rules.
No version-chain semantics.
No CURRENT/HISTORY semantics.
No WAL/recovery or durable-format changes.
No optimizer/join/benchmark-threshold changes.
