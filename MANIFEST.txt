F08-F transaction-status ledger lock-lifecycle fix

Classification:
  production integration defect in the default-OFF F08-F experimental path

Root cause:
  The first transaction-status ledger reload used the caller's RawStore
  transaction. Under container locking, closing the read handle retained the
  metadata-container lock until the caller transaction ended. The existing
  nested-top transaction-ID allocator then timed out trying to open the same
  metadata container FOR UPDATE.

Fix:
  Reload committed transaction statuses through a short-lived nested user
  transaction, commit it, then destroy it before returning to the caller.
  This releases the metadata-container read lock before transaction-ID
  allocation or DDL/write work begins.

Semantics intentionally unchanged:
  - transaction-status visibility model
  - transaction ID allocation
  - commit sequence allocation
  - RawStore WAL/undo/recovery authority
  - status-ledger row format
  - commit publication ordering
  - benchmark thresholds/assertions
