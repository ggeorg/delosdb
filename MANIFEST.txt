DelosDB Gen2-C3 F05 base-fetch current-anchor A/B overlay

Purpose
-------
Falsify whether the remaining matched-plan F05 MVCC base-fetch gap is
materially caused by resolving the stable-row directory before every ordinary
non-covering CURRENT-version fetch.

Evidence leading here
---------------------
Accepted/partial improvements:
- read-directory-head-only: ~9.6% Gen2 improvement
- read-head template reuse: ~1.8% additional improvement
- single-pass hinted version decode: ~5.1% additional improvement

Rejected as primary:
- projected version payload-holder reuse
- version-page run/latch reuse

Latest page-run experiment:
  Heap = 0.800615 ms/execution
  Gen2 = 1.312409 ms/execution
  ratio = 1.639252x

The page-run result is slightly worse than the 1.280053 ms single-pass
baseline, so repeated getPage/PageKey work is not the main cause.

Structural difference
---------------------
The ordinary MVCC IndexRowToBaseRow path still does:

  directory physical record
  -> current version physical record
  -> payload

DelosDB already maintains a CurrentRowAnchor cache containing:
- row id
- current committed version id
- begin sequence
- flags
- current version RecordHint
- directory RowLocation

Experiment
----------
OFF by default:
  existing directory-first base-fetch path

ON:
  -Ddelosdb.experimental.mvccBaseFetchCurrentRowAnchor=true

For a read-only non-A1 fetch with no prefetched directory, the controller:
1. checks for a local pending version;
2. looks up the existing CurrentRowAnchor;
3. requires it to be snapshot-visible and non-tombstone;
4. decodes the anchored current version directly;
5. validates anchored version identity/sequence/flags through the existing
   MvccRawStoreVersionReader.findAnchoredCurrent() contract;
6. falls back to the existing directory-first path on any miss/staleness.

This is diagnostic only. Do not promote directly from this overlay.

No changes
----------
No RowLocation durable format.
No SQL index format.
No visibility rules.
No mutation/update/delete path changes.
No CURRENT/HISTORY semantics.
No RawStore WAL/recovery or durable-format changes.
No optimizer/join/benchmark-threshold changes.
