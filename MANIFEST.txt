DelosDB Gen2-C3 F05 batched base-fetch A/B overlay

Purpose
-------
Falsify whether scalar INDEX_TO_BASE_ROW execution is the primary remaining
F05 selective-join bottleneck by batching a bounded group of index RowLocations
and decoding rows from the same Gen2-C3 CURRENT page under one page latch.

Evidence
--------
The F05 covering control changes only the inner indexes and moves Gen2 from:
  2140 tx/s non-covering
to:
  3462 tx/s covering
while PostgreSQL remains essentially flat:
  3397 -> 3402 tx/s

The forced plan decomposition proves the same nested-loop shape and row/open
counts before and after covering. Non-covering has exactly two
INDEX_TO_BASE_ROW nodes; covering has zero.

Experiment
----------
OFF by default.

Enable both:
  -Ddelosdb.experimental.indexToBaseRowBatchFetch=true
  -Ddelosdb.experimental.mvccBaseFetchBatch=true

Optional:
  -Ddelosdb.experimental.indexToBaseRowBatchSize=16

SQL engine:
- IndexRowToBaseRowResultSet looks ahead up to the bounded batch size.
- Source rows are detached so logical result order is preserved.
- The optional access-method batch API receives corresponding RowLocations.

Gen2-C3 access method:
- read-only statement-snapshot controllers only;
- groups supplied CURRENT RowLocations by physical page;
- latches each referenced CURRENT page once;
- decodes every matching row from that page;
- writes each result into its original batch slot;
- any miss/stale hint/invisible row falls back to the existing scalar fetch.

No semantic changes
-------------------
No result reordering.
No optimizer or join-strategy changes.
No UPDATE/DELETE path changes.
No visibility/CURRENT/HISTORY changes.
No RawStore WAL/recovery or durable-format changes.
No benchmark thresholds or semantic-oracle weakening.

Diagnostic only. Do not promote directly from this overlay.
