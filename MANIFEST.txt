DelosDB Gen2-C3 F05 primary-key-suffix secondary-index control

Purpose
-------
Emulate the intended physical effect of automatically carrying primary-key
identity in non-unique secondary indexes, without changing the storage engine.

Matched workloads
-----------------
JOIN_3WAY_SELECTIVE
  ORDER(customer_id)
  LINE(order_id)

JOIN_3WAY_SELECTIVE_PK_SUFFIX
  ORDER(customer_id, id)
  LINE(order_id, id)

The PK-suffix workload REPLACES the original secondary indexes with the
composite versions. It does not create duplicate alternative indexes.

The SQL query, table rows, result cardinality, six SERVER engines, Gen2-C3
settings, deterministic statistics, and semantic oracle are otherwise the same.

Why this control comes before production design
-----------------------------------------------
Current Derby B-tree storage requires nKeyFields == physical row width, so true
non-key INCLUDE columns are not yet physically supported.

Appending PK identity as a trailing key is physically valid for these
non-unique secondary indexes and is a faithful performance proxy for automatic
PK suffixing. A transparent production implementation would still require
separating logical index columns from hidden physical stored columns so JDBC
metadata, index sharing, ALTER logic, uniqueness semantics, and DDL remain
unchanged.

Diagnostic only. No production engine, optimizer, storage, WAL/recovery,
durable-format, or benchmark-threshold changes.
